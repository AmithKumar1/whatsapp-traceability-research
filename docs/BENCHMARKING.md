# Benchmarking & Evaluation Methodology

Canonical repository: https://github.com/AmithKumar1/whatsapp-traceability-research  
Schema: `opentrace.benchmark.v1` (`schemas/benchmark-report.schema.json`)  
Scope: Empirical performance, storage, and structural disclosure evaluation for synthetic messaging traceability models.

---

## 1. Purpose & Guiding Principles

This document specifies the standard measurement protocols, workload configurations, statistical dispersion metrics, hardware disclosures, and interpretation rules for benchmark reports generated by the WhatsApp Traceability Research Lab.

Scientific reproducibility requires that performance measurements be:
1. **Methodologically bounded:** Separating linear propagation chains from exponential tree structures.
2. **Statistically robust:** Reporting central tendency (median) and dispersion (Interquartile Range) rather than misleading single-run numbers.
3. **Environmentally contextualized:** Documenting physical memory, CPU cores, processor model, OS, and Python runtime.
4. **Epistemically honest:** Explicitly differentiating synthetic in-memory proxies from production wire protocols.

---

## 2. Workload Alignment & Standard Configurations

The benchmark harness tests two distinct forwarding topologies across standardized geometric parameter series:

### 2.1 Linear Forwarding Path Workload
- **Topology:** Unidirectional forwarding chain $v_0 \to v_1 \to \dots \to v_L$, where $v_0$ is the originator and $v_L$ is the final recipient.
- **Hop Count Series:** Evaluates power-of-two hop series:
  $$L \in \{1, 2, 4, 8, 16, 32\}$$
  (Extended series supports $L \in \{64, 128, 256\}$ for stress evaluation).
- **Message Payloads:** Configurable message sizes ($M \in [1, 1{,}000{,}000]$ bytes), defaulting to 256 bytes.
- **Adapter Tested:** `traceback2019-synthetic-path` (simulating predecessor pointer traversal).

### 2.2 Branching Forwarding Tree Workload
- **Topology:** Complete directed tree with uniform branching factor $B$ and depth $D$.
- **Configurations:**
  - Depth series: $D \in \{1, 2, 3\}$ (maximum supported $D \le 6$).
  - Branching factors: $B \in \{2, 3\}$ (supported factors $B \in [2, 5]$).
- **Scale Calculation:**
  $$N_{\text{nodes}} = \sum_{d=0}^{D} B^d = \frac{B^{D+1} - 1}{B - 1}, \quad N_{\text{edges}} = N_{\text{nodes}} - 1$$
  - $(D=3, B=2) \implies 15 \text{ nodes}, 14 \text{ edges}$.
  - $(D=3, B=3) \implies 40 \text{ nodes}, 39 \text{ edges}$.
- **Workload Safety Cap:** The harness enforces an aggregate threshold:
  $$\text{Workload Runs} = \text{repeats} \times \sum_{D} \sum_{B} N_{\text{nodes}} \le 250{,}000$$
  Combinations exceeding this bound are rejected immediately to protect against memory exhaustion.
- **Adapter Tested:** `traceback2019-synthetic-tree` (simulating full tree reconstruction).

## 3. High-Resolution Timing & Measurement Protocol

### 3.1 Timing Clock
All measurements use the monotonic high-resolution operating system timer:
```python
time.perf_counter_ns()
```
This avoids clock-step skew from NTP synchronization.

### 3.2 Phase Separation
Timings are measured and recorded separately for two distinct operational phases:
1. **Construction Phase (`construction_ns_*`):**
   - Measures sender initialization, forwarder metadata generation, cryptographic key derivation, and predecessor state insertion.
2. **Trace Phase (`trace_ns_*`):**
   - Measures server-side lookup, recursive/iterative predecessor traversal, and graph assembly.

### 3.3 Repetitions & Execution Rules
- Default evaluation requires at least $N \ge 3$ repeated trials (recommended $N \ge 5$).
- Each trial runs against fresh, uncorrupted synthetic state to measure realistic uncached execution paths.
- Raw observation values are retained in `samples_ns.construction` and `samples_ns.trace` for distribution fitting.

---

## 4. Statistical Reporting Standards

Due to operating system thread preemption, memory allocation pauses, and CPU frequency throttling, raw timings exhibit positive skew. Therefore, reports follow non-parametric summary statistics:

| Metric Field | Definition | Purpose |
| :--- | :--- | :--- |
| `*_ns_median` | $\text{Median}(X) = Q_2$ | Primary robust measure of central tendency. |
| `*_ns_iqr` | $\text{IQR} = Q_3 - Q_1$ | Primary measure of statistical dispersion across trials. |
| `*_ns_min` | $\min(X)$ | Lower performance boundary (closest to theoretical hardware minimum). |
| `*_ns_max` | $\max(X)$ | Upper outlier boundary (captures scheduling spikes). |
| `samples_ns` | $[x_1, x_2, \dots, x_N]$ | Unaggregated raw timing observations. |

The Interquartile Range (IQR) is calculated using standard 4-quantiles (`statistics.quantiles(values, n=4)`). For sample sizes $N < 2$, IQR defaults to 0.

## 5. Hardware & Environmental Disclosure

To ensure benchmarks can be meaningfully contextualized, the `environment` block records:

```json
"environment": {
  "python": "3.14.7",
  "implementation": "CPython",
  "platform": "Windows-11-10.0.26200-SP0",
  "machine": "AMD64",
  "processor": "Intel64 Family 6 Model 167 Stepping 1, GenuineIntel",
  "cpu_count": 16,
  "total_memory_bytes": 34218831872
}
```

- **Physical Memory (`total_memory_bytes`):** Captured safely via standard platform APIs (`GlobalMemoryStatusEx` on Windows, `os.sysconf` on Linux/macOS).
- **CPU Information (`processor`, `cpu_count`):** Quantifies available thread parallelism and architectural microarchitecture.

## 6. Interpretation Cautions & Measurement Boundaries

External researchers and evaluators must adhere to five measurement boundaries when interpreting benchmark reports:

1. **Serialized JSON Size vs. Protocol Wire Footprint:**
   - `serialized_trace_bytes` measures the compact JSON representation of recovered identifiers (`{"mode":"path","recipient_to_origin_ids":[...]}`).
   - It is **not** a measurement of binary wire protocols, encrypted transport envelopes, or reference protocol wire sizes.
2. **In-Memory Entries vs. Storage Overhead:**
   - `state_entries` counts dictionary keys in the Python adapter.
   - It does not quantify database index structures, disk serialization, WAL logs, or operational retention overhead.
3. **Cross-Topology Comparability:**
   - Path workloads ($O(L)$ linear growth) and tree workloads ($O(B^D)$ exponential growth) model fundamentally different communication patterns.
   - Path timings and tree timings must not be presented as a direct competitive benchmark against one another.
4. **Structural Disclosure vs. Privacy Analysis:**
   - `node_disclosure_fraction` ($|V_{\text{recovered}}| / |V_{\text{scenario}}|$) measures graph reconstruction accuracy relative to the synthetic scenario.
   - It does not measure resistance to traffic analysis, side-channel metadata inference, or cryptographic anonymity.
5. **Non-Interoperability & Synthetic Scope:**
   - All adapters report `interoperable_with_reference: false`.
   - Results are research prototypes for algorithmic scaling evaluation, not performance certifications for production deployment.

## 7. Execution Commands

### Running the Benchmark CLI
```bash
python -m opentrace benchmark \
  --message-size 256 \
  --max-hops 32 \
  --max-tree-depth 3 \
  --branching-factors 2,3 \
  --repeats 5 \
  --out artifacts/benchmark.json
```

### Validating the Benchmark Report Schema
```bash
python -c "
import json, jsonschema, pathlib
report = json.loads(pathlib.Path('artifacts/benchmark.json').read_text())
schema = json.loads(pathlib.Path('schemas/benchmark-report.schema.json').read_text())
jsonschema.validate(report, schema)
print('Benchmark report matches schema!')
"
```
