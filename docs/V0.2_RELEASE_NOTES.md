# WhatsApp Traceability Research Lab v0.2 release notes

**Release date:** 2026-10-23  
**Status:** Alpha research release; not production-ready  
**Version:** `0.2.0`

## What changed from v0.1

### Evidence package hardening

- Manifest v0.2 records each payload file's size and SHA-256 digest.
- The signing public-key fingerprint is included in the signed manifest and checked on verification.
- All payload files must be listed; unlisted files and symlinks fail verification.
- Reserved manifest control files cannot be listed as payloads.
- Relative paths are validated against traversal, backslash, drive, non-canonical spelling, and symlink cases.
- Input JSON rejects duplicate property names, malformed UTF-8, NaN/Infinity, and oversized JSON documents.
- Manifest and record fields are checked exactly, and record counts/hex digests/path order are validated.

### Authorization policy lab

- The signed approval binds a SHA-256 digest of the full request, the approver ID, role, trust domain, decision, and timestamp.
- A configured policy may require distinct approvers and trust domains, certain roles, limited validity windows, and allowed disclosure modes.
- Every public key is fingerprint-pinned in the configured trust registry; registry and policy fields are validated strictly, and key paths must remain relative to the trust directory.
- The output explicitly means `AUTHORIZED_BY_CONFIGURED_POLICY`; it is not a legal finding. The trust store and policy must be protected independently, and the code does not validate a real court/competent-authority order.
- Operational replay prevention, key revocation, trusted time, and a signed policy registry are still required for a real deployment.

### Transparency proof lab

- Local Merkle roots and inclusion proofs use SHA-256 with distinct leaf/node prefixes following the tree-hash convention in RFC 9162.
- A standalone command verifies inclusion using externally supplied bytes, and rejects modified entries/proof paths. Inputs have entry-count and per-entry-size caps, and tree hashing uses index ranges rather than repeated recursive list slicing.
- A reproducible benchmark measures local root, proof-generation, and proof-verification time.
- No signed tree head, consistency proof, online append-only log, external witness, or equivocation detection service exists yet. These proofs must not be represented as a complete transparency system.

### Test and CI improvements

- 49 automated tests cover synthetic tracing, authorization scope, expiry, trust domains, signature/request binding, inventory completeness, input-path constraints, long event chains, Merkle proof trees with sizes 1–19, and schema compatibility.
- CI matrix is configured for Python 3.11–3.13 on Ubuntu, Windows, and macOS.

## Explicitly not implemented

- The published 2019 / 2021 / 2025 / 2026 E2EE cryptographic source-tracing schemes themselves.
- Any WhatsApp API or production integration.
- Lookup/retrieval of chats, backup state, deleted messages, or forwarding history from a phone number.
- RFC 3161 trusted timestamp validation, full RFC 8785 canonical JSON, or production RFC 9162 log service.
- Real identity resolution, legal adjudication, production key management, or admissibility conclusions.

## Recommended next release gates

1. Replace the restricted canonicalizer with a maintained RFC 8785 implementation and run official test vectors across Python and Rust.
2. Add policy/approval and manifest fuzz/property-based tests.
3. Implement signed tree heads and consistency proofs, then build independent monitor/witness tests for split-view detection.
4. Reproduce the existing 2019 Rust implementation and paper benchmarks in an isolated toolchain; document exact deviations before creating an adapter.
5. Commission external cryptography/security review before handling real case material or enabling any real trace operation.
